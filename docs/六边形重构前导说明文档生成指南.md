# 六边形重构前导说明文档生成指南

> 目标：当 PvZ 时间轴播报器进行六边形架构重构前，需要一份“六边形重构前导说明”来记录现状。此指南列出章节结构、内容要求、资料校验与写作规范，特别针对当前代码（已取消 per-event `lead` 字段，仅保留全局提前设置）的最新状态。

---

## 文档整体结构

请严格覆盖以下章节，可在单页中分节或拆成多文档，但所有要点必须包含：

1. **文档说明**
2. **系统现状概览**
3. **运行场景与用例流程**
4. **领域模型与数据结构**
5. **技术现状：端口 / 适配器**
6. **重构展望与 Gap 分析**
7. **附录**

每章建议最少包含的内容如下。

### 1. 文档说明
- 文档目的、适用范围（桌面端 PyQt6 客户端）。
- 成文基线（Git commit，例如通过 `git rev-parse HEAD` 获取）。
- 目标读者（开发、架构、领域专家）。
- 变更记录表（版本、日期、作者、摘要）。

### 2. 系统现状概览
- **系统上下文图**：展示用户、PyQt UI、OCR Agent、TTS、文件系统、设置存储等交互；需注明通信方式（信号、文件 IO 等）。
- **模块职责表**：列出核心模块（`MainWindow`、`TimelineModel`、`TimelineEvent`、`TTSWorker`、`OcrTimerAgent`、文件解析器），列明职责、输入、输出、外部依赖。
- **依赖总览**：Python 版本、PyQt6、pyttsx3（含降级策略）、pandas/openpyxl（Excel 可选）、OpenCV/pyautogui（OCR 侧）等。

### 3. 运行场景与用例流程
- 至少包含：加载 CSV/TXT、加载 Excel、多流程切换、开始/暂停/重置、OCR 自动对时、TTS 播报、导出样例 CSV、迷你模式切换。
- 每个用例需要：
  1. 参与者
  2. 前置条件 / 触发方式
  3. 主流程步骤（最好配顺序图或时序表，标明关键函数/信号）
  4. 异常或替代流程
  5. 输入/输出数据（例如 `TimelineEvent` 列表、TTS 文本）

### 4. 领域模型与数据结构
- **领域词汇表**：定义流程 Flow、TimelineEvent、全局提前秒、OCR ROI、迷你模式等，并给出代码引用（文件:行号）。
- **数据结构表**：列出 `TimelineEvent`（现仅含 `time_ms/action/population/note`）、`flows` 字典、`QSettings` 存储项、TTS 队列等，说明来源和使用者。
- **业务规则**：使用 bullet 列出关键约束，例如：
  - QTimer 100 ms tick 驱动手动计时。
  - 提前播报仅使用全局提前秒（CSV/Excel `lead` 列已废弃，写入也被忽略）。
  - 每个 tick 最多播一条语音。
  - OCR 未锁定时不推进计时。

### 5. 技术现状：端口 / 适配器
- 结合未来六边形架构，将当前实现映射到潜在端口：
  - 输入适配器：PyQt UI 事件、OCR 信号、文件导入按钮。
  - 输出适配器：TTSWorker、文件写入、设置存储。
- 描述关键耦合点（UI 直接拥有 TTS/OCR/解析逻辑）以及线程边界（TTS QThread、OCR 信号）。

### 6. 重构展望与 Gap 分析
- 绘制或描述目标的 Hexagonal 结构（领域核心、应用服务、端口/适配器）。
- 对比现状，列出差距（领域逻辑散落 UI、无仓储抽象、依赖难替换）。
- 提出阶段性建议（例如：抽象 `TimelineService`、封装文件仓储/偏好存储、定义 `SpeechPort/OcrPort`、再重构 UI）。

### 7. 附录
- 参考资料列表（源码文件、外部文档、issue 等）。
- 术语/缩写表（TTS、OCR、ROI 等）。
- 未决问题列表（例如：OCR 依赖替换计划、迷你模式保留与否、是否重新引入 per-event 提前量）。

## 内容要求与校验清单

完成文档前请执行以下步骤，确保准确性：

1. **基线确认**：使用 `git rev-parse HEAD` 记录版本；若之后更新需刷新记录。
2. **依赖核对**：通过 `pip list` 或 requirements 收集版本，注明可选依赖的降级路径。
3. **功能验证**：对列出的用例至少做一次走查（可手动），确认描述与代码一致。
4. **引用准确**: 提及实现细节时引用 `文件:行号`（例如 `pv_z_时间轴播报器（python_py_qt_6_）.py:500`）。
5. **图示**：上下文图、用例顺序图等可使用 Mermaid/PlantUML；若缺工具，需通过清晰文字说明补足。
6. **评审**：完成后让熟悉业务的成员复核，确认无遗漏或过时信息。

---

## 写作规范

- **语气**：客观、事实描述，明确标注假设或 TODO。
- **结构**：使用二级/三级标题、表格、项目符号，提高可读性。
- **版本控制**：将文档置于仓库（建议 `docs/`），并在 README 提供链接。
- **维护**：每次架构里程碑后更新文档，保持与实现同步；更新时刷新变更记录。
- **编码**：保存为 UTF-8，避免因编码导致的 diff 噪声。
